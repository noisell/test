# Инцидент: зеркало каталога

Сервис переносит изменения товаров из локальной таблицы исходящих событий во
внешний интерфейс пакетного обновления каталога. После перехода поставщика на
вторую версию мониторинг выявил редкие расхождения: один товар помечается
опубликованным вместо другого, после истечения срока, отведённого обработчику,
иногда учитывается запоздалый ответ, а при ошибке фиксации транзакции часть
набора уже успевает изменить состояние.

В starter-репозитории находятся существующий компонент, тесты, обезличенный
журнал инцидента `incident/sample.log` и публичное описание взаимодействия с
поставщиком `docs/upstream-contract.md`.

Журнал — диагностический снимок наблюдаемого поведения production-компонента в
момент сбоя; он не задаёт отдельный формат API.

Разберитесь в причинах инцидента и внесите необходимые изменения в компонент.

## Критерии приёмки

- результаты сопоставляются с операциями по идентификатору операции (operation
  ID), а не по позиции в ответе; порядок результатов провайдера не гарантирован;
- пакетный ответ может одновременно содержать результаты со статусами
  `accepted`, `retryable` и `rejected` — каждый из них обрабатывается согласно
  контракту;
- если ответ неполон, содержит повторяющиеся результаты или неизвестную
  операцию, изменения не применяются частично: весь набор операций направляется
  на безопасную повторную обработку;
- при транспортной ошибке весь набор операций направляется на повторную
  обработку с теми же стабильными идентификаторами;
- все результаты набора сохраняются одновременно и только пока он закреплён за
  текущим обработчиком. Если срок закрепления (lease) истёк, запоздалый ответ не
  применяется; если фиксация транзакции завершилась ошибкой, состояние ни одной
  операции не меняется;
- подтверждение старой версии после появления более новой завершает старую
  операцию как устаревшую (`obsolete`) и не откатывает опубликованную версию;
- отчёт и метрики отражают только действительно сохранённые переходы;
- добавлены тесты не только успешного сценария, но и обработки ошибок и
  нарушения основных инвариантов. Отдельная группа оценивает способность этих
  тестов обнаруживать поведенческие дефекты; одного smoke-теста недостаточно.

Разрешено менять все файлы starter-репозитория. Нельзя добавлять внешние
зависимости.

## Запуск

```bash
python3 -m unittest discover -s tests -p 'test_*.py'
```

Публичные regression-тесты в starter воспроизводят часть инцидента и изначально
не проходят. Это ожидаемо.

## Как оцениваются ваши тесты

Добавьте тесты в `tests/test_candidate.py`. Сначала они запускаются на
реализации, удовлетворяющей публичному контракту, а затем — на пяти вариантах с
отдельными поведенческими дефектами. За обнаружение каждого дефекта начисляется
2 балла. Используйте только публичные интерфейсы и не проверяйте точные тексты
диагностических причин, если они явно не определены контрактом.

## Оценивание

- базовое поведение компонента — 10;
- корреляция результатов по operation ID — 25;
- смешанные статусы результатов — 20;
- некорректные ответы Bulk API — 15;
- подтверждение устаревшей версии — 15;
- атомарное завершение с проверкой срока закрепления (lease fencing) — 5;
- тесты взаимодействий кандидата — 10.

Всего 100 баллов.

## Использование AI и защита

AI-инструменты разрешены, но не обязательны. Заполните `DEFENSE.md`. Если при
решении использовали чат, приложите экспорт диалога отдельным файлом
`AI_DIALOG.md`, `.txt` или `.json`; чувствительные данные можно удалить. Наличие
и содержание диалога напрямую на автоматический балл не влияет.
