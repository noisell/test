# Контракт Catalog Bulk API v2

`POST /v2/catalog/bulk` принимает от 1 до 100 операций. `operation_id` создаётся
клиентом, глобально уникален и является idempotency key: повтор запроса с тем же
идентификатором и тем же содержимым возвращает прежний логический результат.

Каждый элемент ответа содержит исходный `operation_id` и один статус:
`accepted`, `retryable` или `rejected`. У `retryable` может быть
`retry_after_seconds`, у `rejected` — диагностический `reason`.

Порядок элементов `results` произвольный и не связан с порядком запроса. Для
валидного ответа множество `operation_id` совпадает с множеством запроса: нет
пропусков, повторов и неизвестных идентификаторов. Нарушение этого свойства
означает некорректный/обрезанный ответ, даже если HTTP-статус равен 200. Такой
ответ нельзя частично применять; весь batch безопасно повторить благодаря
idempotency key.

Транспортный сбой и невалидный JSON имеют ту же retryable-семантику для всей
пачки. `rejected` является терминальным бизнес-ответом только для названной
операции.

Поле отчёта `protocol_errors` считает только структурно некорректные ответы
Bulk API: пропуски, повторы и неизвестные `operation_id`. Транспортная ошибка
направляет всю пачку на повторную обработку, но не увеличивает
`protocol_errors`. Точный диагностический `reason` для повторной обработки не
является частью публичного контракта.
